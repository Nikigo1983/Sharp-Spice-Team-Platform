# Week View vs Month View — анализ для Sharp & Spice

**Дата:** 2026-06-22  
**Статус:** аналитический документ — код, PR, commit, deploy не затрагиваются  
**Контекст:** платформа Sharp & Spice (релокация / эмиграция), календарь MVP после PR #5 (Day View)  
**Команда:** 1 owner (Вероника) + 3 manager (Злата, Юля, Руслан) — **4 пользователя**

---

## Executive Summary

| Режим | Суть для Sharp & Spice | Сильная сторона |
|-------|------------------------|-----------------|
| **Month View** | «Какая неделя/день загружены по подачам и дедлайнам?» | Обзор месяца, all-day события, точка входа |
| **Week View** | «Когда у меня окно для консультации в четверг?» | Почасовое планирование, пересечения слотов |

**Рекомендация:** следующим реализовать **PR #6 — Month View** (не Week).

**Почему:** Month — **default view** при открытии `/calendar`; сейчас пользователь видит placeholder. Day View (PR #5) уже закрывает ежедневную работу менеджера. Month даёт стратегический обзор owner и лучше подходит под дедлайны и подачи документов. Week сложнее в реализации и частично дублируется связкой Month → Day.

---

## Контекст использования календаря в Sharp & Spice

### Бизнес-модель

- Агентство релокации: консультации, сбор документов, подача в госорганы, сопровождение кейсов.
- CRM (Google Sheets / клиенты) — основной источник статусов; календарь MVP пока **автономный** (без CRM linkage до Phase 2).
- Два слоя событий MVP:
  - **personal** (синий) — консультации, личная занятость менеджера;
  - **company** (зелёный) — подачи, командные встречи, общие даты.

### Текущее состояние продукта (после PR #5)

| View | Статус |
|------|--------|
| Day | ✅ Agenda, сортировка, цвета |
| Month | ⏳ Placeholder (default при входе) |
| Week | ⏳ Placeholder |

---

## 1. Week View

### Описание

7 колонок (Пн–Вс), почасовая сетка **07:00–20:00**, all-day полоска сверху. События — блоки по длительности; overlap — vertical stack (MVP).

### Типичные сценарии менеджеров

| Сценарий | Описание | Частота* |
|----------|----------|----------|
| Планирование консультаций | Найти свободный 1-часовой слот на этой неделе | **Высокая** (ежедневно) |
| Сверка с подачей | «В пятницу общая подача — не ставлю консультацию в 14:00» | Средняя (1–2×/нед) |
| Блокировка времени | Закрыть слот под звонок / поездку в консульство | Средняя |
| Командный синк | Увидеть зелёное company-событие в колонке среды | Низкая–средняя |

\*Оценка для команды 3 менеджеров при активном использовании календаря.

### Типичные сценарии owner

| Сценарий | Описание | Частота* |
|----------|----------|----------|
| Загрузка менеджеров | Сравнить колонки Златы/Юли/Руслана по часам | Низкая (MVP: personal не видны между менеджерами) |
| Координация подач | Убедиться, что company-событие не пересекается с внутренней встречей | Средняя |
| Оперативный контроль недели | «Что у команды на этой неделе?» | Средняя |

**Ограничение MVP:** owner **не видит** personal events других менеджеров — Week для owner показывает в основном **company**-слой и свои личные события.

### Частота использования (прогноз)

| Роль | Оценка | Комментарий |
|------|--------|-------------|
| Manager | **3–5×/нед** | Если календарь станет основным инструментом записи |
| Owner | **1–2×/нед** | Чаще через company-события |

**Итого по команде:** ~10–17 открытий Week View в неделю при полном adoption.

### Сложность реализации

| Аспект | Оценка | Детали |
|--------|--------|--------|
| UI | **Высокая** | Time rail, 7 колонок, scroll sync, all-day row |
| Layout | **Высокая** | `layoutDayEvents`, overlap stack, TZ |
| Тесты | Средняя | Unit для `week.ts` + ручной QA overlap |
| Риски | **High** (overlap, mobile scroll) | По `CALENDAR_IMPLEMENTATION_PLAN.md` |
| Оценка трудозатрат | **~2 рабочих дня** | PR #7 в плане |

### Ценность для бизнеса

| Критерий | Оценка (1–5) | Комментарий |
|----------|--------------|-------------|
| Скорость записи консультаций | **5** | Клик по слоту (PR #8) — лучший UX для booking |
| Снижение двойных броней | **4** | Визуальные пересечения в одной неделе |
| Координация команды | **3** | Только company-слой виден всем |
| Onboarding / простота | **2** | Сложнее Month; на mobile — fallback на Day |

## 2. Month View

### Описание

Сетка 7×5/6, чипы событий в ячейках дня, max 3 + «+N ещё», клик по дню → Day View. **Default** при открытии `/calendar`.

### Типичные сценарии менеджеров

| Сценарий | Описание | Частота* |
|----------|----------|----------|
| Обзор месяца | «Когда у меня плотные недели?» | **Высокая** (2–3×/нед) |
| Подготовка к подаче | Увидеть зелёное company-событие на 25-е | Средняя |
| Переход к дню | Клик по дате → Day agenda с деталями | **Высокая** |
| Планирование отпуска / выходных | All-day блок на диапазон дат | Низкая (редко) |

### Типичные сценарии owner

| Сценарий | Описание | Частота* |
|----------|----------|----------|
| Операционный обзор | Сколько company-событий в месяце (подачи, собрания) | **Высокая** |
| Планирование нагрузки | Выбрать неделю для общего собрания | Средняя |
| Коммуникация с командой | «Смотрите, 30 июня — день подачи» | Средняя |
| Стратегия | Распределение пиков по месяцам | Низкая–средняя |

### Частота использования (прогноз)

| Роль | Оценка | Комментарий |
|------|--------|-------------|
| Manager | **5–10×/нед** | Default view — каждый вход в календарь |
| Owner | **3–5×/нед** | Обзор company-календаря |

**Итого по команде:** ~20–35 открытий Month View в неделю — **выше**, чем Week, за счёт default.

### Сложность реализации

| Аспект | Оценка | Детали |
|--------|--------|--------|
| UI | **Средняя** | CSS grid, чипы (reuse `CalendarEventChip`) |
| Layout | **Средняя** | `buildMonthMatrix`, `eventsForDay` |
| Тесты | Средняя | Unit для `month.ts` |
| Риски | Medium (overflow chips) | «+N ещё» + drill-down в Day |
| Оценка трудозатрат | **~1.5 рабочих дня** | PR #6 в плане |

### Ценность для бизнеса

| Критерий | Оценка (1–5) | Комментарий |
|----------|--------------|-------------|
| Первое впечатление / adoption | **5** | Убирает placeholder на главном экране |
| Дедлайны и all-day | **5** | Дата-ориентированные события |
| Координация подач | **4** | Company-события видны всей команде |
| Почасовое планирование | **2** | Нужен Day или Week для деталей |

## Оценка по типам событий Sharp & Spice

### Консультации клиентов

| | Week | Month |
|---|------|-------|
| **Характер** | Personal, 30–90 мин, в рабочие часы | Точка на дате; время — в Day |
| **Лучший view** | **Week** (идеально) | Month как индекс → Day |
| **MVP сейчас** | — | Day View **уже закрывает** дневной сценарий |
| **Phase 2** | + CRM linkage, `event_type=consultation` | Меньше ценности без времени |

**Вывод:** Week выигрывает для booking, но **Day View (PR #5) уже даёт 80% ценности** до появления Week.

---

### Подачи документов

| | Week | Month |
|---|------|-------|
| **Характер** | Company, часто привязка к **конкретной дате** (иногда all-day) | Видны всей команде |
| **Лучший view** | Week — если есть точное время | **Month** — «когда подача в июле» |
| **Типичный пользователь** | Менеджер на месте подачи | Owner планирует дату для всех |

**Вывод:** **Month предпочтительнее** для координации подач на уровне команды.

---

### Дедлайны

| | Week | Month |
|---|------|-------|
| **Характер** | All-day, date-centric (Phase 2: `client_deadline`, CRM virtual) | Критично видеть **плотность дат** |
| **MVP** | Не реализованы (Phase 2) | Month готовит UX под overlay дедлайнов |
| **Аналог сегодня** | Задачи (overdue) в Tasks | Календарь — даты, не часы |

**Вывод:** **Month существенно ценнее** для дедлайнов; Week почти не добавляет value для all-day.

---

### Внутренние встречи команды

| | Week | Month |
|---|------|-------|
| **Характер** | Company, 30–60 мин, 1×/нед или 2×/мес | Company, фиксированная дата |
| **Лучший view** | **Week** — найти общий слот | **Month** — «собрание 20-го» |
| **Размер команды** | 4 человека — ручная координация возможна | Достаточно |

**Вывод:** Паритет; при 4 пользователях **Month + Day** достаточно до Phase 2.

## Риски отложенного Month

| Риск | Если Week первым | Митигация |
|------|------------------|-----------|
| Плохой UX при входе в `/calendar` | Default = Month остаётся placeholder ещё ~2 дня | Month первым |
| Менеджер без Week | Переключается на **Day** (уже есть) | Приемлемо до PR #7 |
| Owner без обзора месяца | Не видит картину по подачам | Month приоритетнее |

## Риски отложенного Week

| Риск | Если Month первым | Митигация |
|------|-------------------|-----------|
| Нет почасовой сетки | Day View + ручной выбор времени в CRUD (PR #8) | Временно OK |
| Slot-click create | Откладывается до PR #7+#8 | Create через кнопку toolbar |

## Рекомендация

### Реализовывать следующим: **PR #6 — Month View**

**Обоснование (кратко):**

1. **Month — default view.** Каждое открытие `/calendar` сейчас показывает placeholder — это главный UX-разрыв.
2. **Day View уже реализован (PR #5)** и покрывает сценарий «мои консультации сегодня/в этот день» лучше, чем ожидание Week.
3. **Month → Day** — естественный drill-down, уже заложенный в wireframes и spec.
4. **Подачи, дедлайны, company-события** — date-first; Month даёт больше бизнес-ценности для Sharp & Spice.
5. **Ниже сложность и риск** (~1.5 vs ~2 дня; меньше overlap/layout проблем).
6. **Week остаётся PR #7** и станет максимально полезен после **PR #8 (CRUD)** — slot-click create.

### Когда пересмотреть порядок

Перейти на Week-first, если после PR #8 выяснится, что:

- менеджеры **не используют** Day View для записи консультаций;
- >50% событий — **короткие слоты** с пересечениями в одной неделе;
- owner требует **почасовой** сводки по company-событиям (маловероятно в MVP RBAC).
